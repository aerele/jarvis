| 1 | **BLOCKER** | `jarvis/tools/resolve_links.py:64-68` and `:90-97` (choice passes), `_resolve_choice` `:275-306` — no permission gate anywhere | **EC-12 is violated: the choice pass IS a new information-disclosure channel.** `resolve_links` never checks read permission on the *parent* doctype, and the new pass returns that doctype's docfield option list contents. Proven end to end on `jarvis.local` through the real `jarvis.api.call_tool` dispatch, as a System User holding a `JARVIS_ACCESS_ROLES` role with `frappe.has_permission("Sales Invoice", "read") == False`: `get_schema("Sales Invoice")` → `{"ok":false,"error":{"code":"PermissionDeniedError"}}`, while `resolve_links("Sales Invoice", {"port_code":"Chennai"})` → `{"ok":true,...}` returning `INFCH5/INMAA1/INMAA4/INMAA5/INMAA6` **plus `candidates_total: 6`**. Because matching is case-insensitive substring, this is an enumeration oracle: iterate single characters and read out the whole list `limit` at a time, with the true total handed back each time. The plan's justification — "Assessed as already-safe: `get_schema` exposes the same options" — is **factually false**: `get_schema.py:320-321` raises `PermissionDeniedError`, and every sibling metadata tool is fenced too (`get_creation_context.py:97`, `get_naming_series_preview.py:38`, `get_list.py:112`, `get_doc.py:29`, `describe_customizations` via `fence_for_user`). The Link pass in this very file already honours the contract (`_resolve_one:130` → `unchecked`); the choice pass deliberately does not. Worse, `jarvis/tests/test_resolve_links.py:326-333` (`test_choice_pass_ignores_read_permission`) asserts that choices are **identical** with `has_permission` patched to `False` — the leak is now regression-locked as intended behaviour. | Gate the choice pass on the parent doctype the same way the Link pass gates on the target: if `not frappe.has_permission(doctype, ptype="read")`, emit `unchecked` for every choice field (or emit no `choices` at all). Then invert `test_choice_pass_ignores_read_permission` so it asserts no option content is returned without read, and add a test asserting `resolve_links` and `get_schema` agree on the permission boundary. |
| 2 | **MAJOR** | `jarvis/tools/resolve_links.py:291` (`needle = value.strip()`) with `:294` deciding `exact` | **False `exact` on the unguarded class.** The comparison strips the supplied value, but Frappe only strips the value for `Select` (`base_document.py::_validate_selects` → `self.set(df.fieldname, cstr(...).strip())`). Nothing strips `Autocomplete`, which is a plain data fieldtype. So a padded value is blessed as `exact` and then stored padded. Proven on `jarvis.local`: `resolve_links("Bill of Entry", {"items":[{"gst_treatment":"  Taxable  "}]})` → `{"status":"exact"}`, and `frappe.new_doc("Bill of Entry Item").gst_treatment = "  Taxable  "` keeps `'  Taxable  '`. Same on the flagship field: `port_code: "  INMAA1  "` → `exact`, then `preview_doc` → `valid: true`, `resolved.port_code = "  INMAA1  "`. Downstream, `india_compliance/gst_india/utils/e_invoice.py` guards with `if self.doc.port_code in PORT_CODES:` — `"  INMAA1  "` is not a member, so the Port is **silently omitted from the e-invoice payload**. That is the exact "filed shipping bill carrying a bogus port" outcome the plan opens with, reached *through* an `exact` verdict. Note the asymmetry cuts the wrong way: the one class the server does strip (`Select`) is the one where stripping is safe, and the class it does not strip is where the code strips anyway. No test covers a padded value. | For a non-`Select` field, either do not report `exact` when `value != value.strip()` (report `candidates` with the canonical option so the agent writes the stripped form), or echo the stripped value in `rec["value"]`. Add a test for `"  Taxable  "` on an Autocomplete asserting the agent is steered to the unpadded option. |
| 3 | **MAJOR** | `jarvis/tools/resolve_links.py:255-272` (`_iter_choice_values`) + `:342-343` (`_summary_note`) | **EC-3 is only half implemented, and the half left out is the likeliest one.** `int`/`float`/`bool` are coerced, but a `dict` — and a list of dicts — falls off the end of `_iter_choice_values` and is silently dropped, after which the note affirmatively reads `"all links resolved to existing records"`. Proven: `_iter_choice_values({"value":"INMAA1"})` → `[]`, `_iter_choice_values([{"value":"INMAA1"}])` → `[]`; `resolve_links("Sales Invoice", {"port_code": {"value":"INMAA1","label":"INMAA1 - Chennai (Ex Madras)"}})` → `{"choices": [], "note": "all links resolved to existing records"}`. `{value, label}` is **the exact shape this tool hands back in `candidates`**, and both the descriptor and `SKILL.md` tell the model to "pick one" — so a model that pastes the candidate object back is the single most probable wrong type on this path, and it gets an affirmative all-clear. On a length-capped field (`port_code`, length 15) the write path happens to catch it; on an uncapped Autocomplete (`Bill of Entry Item.gst_treatment`) nothing does. EC-3 requires non-string values to be "never silently dropped, and the note must not read 'all resolved'"; r1 finding #4's required fix named `dict` explicitly. The delivered test `test_non_string_choice_value_coerced_not_dropped` (`test_resolve_links.py:158`) covers only `12345`/`True`/`3.14`. | Emit a record for any supplied non-empty value whose type cannot be resolved (status `missing`, or a dedicated "unsupported value type"), so the note can never read all-clear while a supplied value went unjudged. Extend the EC-3 test to `dict` and `[dict]`. |
| 4 | MINOR | `jarvis/tools/resolve_links.py:234` | r1 MINOR #8 was not addressed. `_parse_options` strips each option line; `_validate_selects` compares against the **unstripped** split (`options = (df.options or "").split("\n")`). Proven: `_parse_options` on `"Open\r\nClosed"` → `[{"value":"Open"},{"value":"Closed"}]` and `_resolve_choice(..., "Open")` → `exact`, while Frappe's membership test is `"Open" in ["Open\r","Closed"]` → `False` → it throws on insert. Not reachable on this bench today (`select ... from tabDocField / tabCustom Field where fieldtype in ('Select','Autocomplete') and options like '%\r%'` → 0 rows on `jarvis.local`), but the module docstring and the plan both claim to mirror `_validate_selects` and this is a silent divergence. | Either stop stripping option lines, or state the deliberate divergence in `_parse_options`'s docstring with a test pinning it. |
| 5 | MINOR | `jarvis/tools/resolve_links.py:202-208` | The robustness guarantee is narrower than the plan claims. The plan says "the whole choice pass is wrapped so a malformed option list … can never break Link resolution", but `_is_resolvable_choice(df)` is called **outside** `_choice_fields`'s `try`, and it ends in `df.options.strip()`. Proven: a docfield whose `options` is a non-string raises `AttributeError: 'int' object has no attribute 'strip'`, which escapes `_choice_fields` → escapes `resolve_links` → takes the pre-existing Link pass down with it. Not reachable from the DB today (the DocField column is text), so this is a latent hole in the stated invariant rather than a live break. | Move the `_is_resolvable_choice` call inside the `try`, or wrap the `for df in meta.fields` body as a whole. |
| 6 | MINOR | `jarvis-persona/skills/jarvis-drafting/SKILL.md` (choice paragraph) and `jarvis-openclaw-plugin/src/tool-defs.ts:190` | Both teach a port code that does not exist: `'Chennai' … finds the code the field wants - 'INMAA'`. `india_compliance`'s `PORT_CODES` has 1005 entries and no `INMAA`; the real codes are `INMAA1`, `INMAA4`, `INMAA5`, `INMAA6` (and `INFCH5` also matches "Chennai"). This is the same class of defect flagged in T6 and reported fixed — a real port code mixed with invented data — and it is now in the text the model actually reads. | Use a real code (`INMAA1`) in both files, or make the example plainly synthetic in both. |
| 7 | MINOR | `jarvis/tools/resolve_links.py:342-343` | `_summary_note`'s all-clear string is still link-only wording (`"all links resolved to existing records"`) on a response that now has two sections. It is emitted verbatim alongside a populated `choices` array (proven: `port_code: "INMAA1"` → one `exact` Autocomplete record **and** that note). Harmless where the choices really are clean, actively misleading in finding 3's case. | Reword to cover both passes, e.g. `"all links and choice values resolved"`, and make the wording conditional on choices having been judged. |
| 8 | MINOR | `jarvis/tools/resolve_links.py:145` vs `:300`; `tool-defs.ts:190` | The key `candidates` carries two different shapes: `{name, title}` under `links[]`, `{value, label}` under `choices[]`. The descriptor documents neither, so nothing tells the model which member to write back. Directly compounds finding 3. | Say in the descriptor that choice candidates carry `value` (what to write) and `label` (what to show), and that `value` is the field value. |
