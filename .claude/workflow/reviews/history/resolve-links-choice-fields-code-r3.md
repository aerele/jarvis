| 1 | **BLOCKER** | `jarvis/tools/resolve_links.py:96` — `child_may_read = may_read and frappe.has_permission(df.options, ptype="read")` | **The child-table half of the feature is dead for every non-Administrator user, and it emits a false warning on correct values.** `df.options` here is a child DocType (`istable=1`), so `frappe.has_permission` routes to `has_child_permission` (`frappe/permissions.py:804-831`), which returns **False whenever neither `child_doc` nor `parent_doctype` is supplied** — which is always, at this call site. `Administrator` short-circuits at `permissions.py:104` before that branch, which is exactly why the whole test suite (run as Administrator) is green on a dead code path. Proven live over real HTTP on `jarvis.local` as a System User holding Sales User / Sales Manager / Accounts User / Jarvis User: `has_permission("Sales Order Item","read") == False`, and `resolve_links("Sales Order", {"items":[{"margin_type":"Percentage"}]})` — a **real, correct option** — returns `{"status":"unchecked", "candidates":[]}` with `note: "1 choice value(s) NOT verified (option list unavailable) - confirm before writing"`. The identical call as Administrator returns `choices: []`. Same on `Sales Invoice.taxes[0].charge_type = "On Net Total"`. The inverse fails too: `margin_type: "PercentageX"` — which `_validate_selects` **will** reject on insert — also reports `unchecked`, so the pass catches nothing in child tables. Blast radius: 121 child-table choice fields in frappe and 83 in erpnext/hrms, including every sales/purchase line (`margin_type`) and every tax row (`charge_type`, `category`, `add_deduct_tax`). This violates the plan's Done condition ("no correct value is ever reported as wrong"), guts EC-8, and contradicts both the code's own comment on `:95` ("Child rows are governed by the parent's permission, like get_list") and `get_schema`'s documented contract (`get_schema.py:308-310`: "Child tables (under `verbose=True`) are part of the parent, not checked separately"). The r2 BLOCKER fix over-corrected: the header gate is right, the child gate is a second, always-failing gate that `get_schema` does not have. | Delete the child-doctype `has_permission` call and gate child choices on `may_read` (the parent) alone, matching `get_schema`. If a child gate is genuinely wanted, it must pass `parent_doctype=doctype`. Add a test that exercises the choice pass **as a non-Administrator user with child rows** — no test in this suite ever leaves the Administrator session, which is what hid this. |
| 2 | **MAJOR** | `jarvis/tools/resolve_links.py:295-305` (`_iter_choice_values`, dict branch) | **EC-3 is still only half fixed — a dict is silently dropped into an affirmative all-clear whenever its `value` key is empty rather than absent.** Only `inner is None` triggers the fallback; `{"value": ""}`, `{"value": "   "}` and `{"value": []}` all recurse into branches that yield nothing at all. Proven live: `resolve_links("Sales Invoice", {"port_code": {"value":"","label":"INMAA1"}})` → `choices: []`, `note: "all links and choice values resolved"`. Same for `{"value":"   "}` and `{"value":[]}`. Inside a list it silently shortens the result: `port_code: [{"value":"INMAA1"},{"value":""},{"label":"x"}]` → 2 records for 3 supplied values. The amended plan is explicit: a dict "is **never silently dropped** — it reports `unchecked` (or resolves via its `value` key) and the note must not read 'all resolved'". `test_dict_and_list_of_dict_choice_values_are_not_dropped` (`test_resolve_links.py:404`) covers only dicts with a usable or absent `value`. | Treat "a dict was supplied but yielded no value" as a record (`unchecked`), never as absence. Extend the EC-3 test to `{"value": ""}`, `{"value": "   "}`, `{"value": []}`, and the list form. |
| 3 | **MAJOR** | `jarvis/tools/resolve_links.py:284-308` (`_iter_choice_values` recurses on both `list` and `dict` with no depth bound) | **A new unhandled HTTP 500 reachable from ordinary tool input.** A choice value nested ~990 levels deep — a ~10 KB request body — parses cleanly through orjson and then blows the Python stack. Proven live on `jarvis.local`: depth 950 → HTTP 200; **depth 990 → HTTP 500 `RecursionError: maximum recursion depth exceeded`, a 4.8 MB Werkzeug traceback, 83 s of worker time**; depth 5000 → orjson rejects it cleanly at the request layer (HTTP 417). So there is a live window (~950–1024) where the payload reaches the tool and there is no defense. This is newly introduced: `_iter_values`, the pre-existing Link path, is not recursive. Plan EC-11 pulled `limit` validation into scope precisely so this tool answers bad input with a clean `InvalidArgumentError` instead of a 500 — this reopens the same class on the same tool. | Bound the recursion (explicit depth counter, or flatten iteratively) and emit an `unchecked` record for anything past the bound. Add a test at the boundary. |
| 4 | **MAJOR** | `jarvis/tools/resolve_links.py:367-389` (`_summary_note`) | **The note says "all links and choice values resolved" while a link was never checked.** `_summary_note` counts only `missing` and `candidates` for links, so a link with `status: "unchecked"` contributes nothing and the function falls through to `ALL_CLEAR_NOTE`. This change made the claim *stronger* than the string it replaced ("all links resolved to existing records"), and the choice side of the very same function handles `unchecked` correctly with its own clause — the link side was left inconsistent. Proven live as a user without Project read: `resolve_links("Sales Invoice", {"project":"ghost-project"})` → `links: [{"status":"unchecked"}]`, `note: "all links and choice values resolved"`. T2's acceptance criterion is a note "that can never say 'all clear' while an unresolved or coerced value exists". | Fold unchecked links into the note — either their own clause or the existing "NOT verified ... confirm before writing" clause. |
| 5 | **MAJOR** | `jarvis/tools/resolve_links.py:289-291` (EC-7 behaviour) | **A whitespace-only choice value gets a full all-clear on a value the insert provably rejects.** `_iter_choice_values` treats `"   "` as absent, but `_validate_selects` (`frappe/model/base_document.py:1106`) skips only *falsy* values — `"   "` is truthy, is stripped to `""` at `:1116`, and then throws at `:1119`. Proven on `test_jarvis`: inserting `ToDo{status: "   "}` raises `ValidationError: Status cannot be "". It should be one of "Open", "Closed", "Cancelled"`, while `resolve_links("ToDo", {"status":"   "})` returns `note: "all links and choice values resolved"` with zero records. Confirmed live over HTTP for `Sales Order{"order_type":"   "}`. On an Autocomplete the same value is stored padded and silently — the exact corruption class this feature exists to stop. EC-7 mandates this behaviour, so the implementation is faithful to a spec that is wrong against the code it claims to mirror. | Report a whitespace-only choice value (only `""`/absent is genuinely absent), or amend EC-7 with the `_validate_selects` evidence and record the accepted gap explicitly. Either way it cannot stay an unremarked false clear. |
| 6 | MINOR | `jarvis/tools/resolve_links.py:302, 308` | Python `repr` leaks into the agent-facing `value`. Live: `port_code: {"label":"INMAA1"}` → `{"value": "{'label': 'INMAA1'}", "status": "missing"}` — the agent is told the value it intends to write is a Python dict literal. The plan specifies `unchecked` for this shape, not `missing`. `repr` is also unbounded, so a large nested dict's repr goes straight into the response. | Emit `status: "unchecked"` with a fixed marker (or omit `value`) rather than a Python literal, and cap the echoed length. |
| 7 | MINOR | `jarvis-openclaw-plugin/src/tool-defs.ts:190` | r2 MINOR #8 was reported fixed by "documented in the module docstring" — Python the model never reads. The **descriptor**, which the model does read, still never states that choice candidates carry `value` (the string to write) and `label` (what to show), nor that `links[]` candidates carry `{name,title}` instead. That omission is precisely what makes handing a candidate object straight back likely — the failure mode finding 2 is about. | Add one clause to the descriptor: choice candidates are `{value, label}`; write `value`. |
| 8 | MINOR | `jarvis-persona/skills/jarvis-drafting/SKILL.md` (choice paragraph) | The persona teaches that `unchecked` "means the option list could not be read (a dynamic, server-loaded source)" — a single cause. The tool also returns `unchecked` on a permission denial (and, per finding 1, on every child table), which `tool-defs.ts:190` does mention. The two documents the model reads disagree on what the status means. | Add the permission cause to `SKILL.md` so it matches the descriptor. |
| 9 | MINOR | `jarvis/tools/resolve_links.py:240` vs the comment at `:251-254` | The comment claims option lines are not stripped "so an option carrying stray whitespace is one Frappe itself will reject", but `:240` strips the whole options blob before splitting, so whitespace on the first/last line is still silently normalised. `"Open\nClosed\r"` yields `exact` for `"Closed"` where `_validate_selects` throws. Not reachable in the shipped corpus (I re-scanned frappe/erpnext/hrms: **0** option lines with stray whitespace), so latent — but the comment overstates the guarantee. | Either drop the outer `.strip()` or narrow the comment to what the code actually does. |
| 10 | MINOR | `jarvis/tools/resolve_links.py:88-89` | A child-table key supplied as a dict instead of a list is skipped with no record and the note reads all-clear. Proven live: `{"items": {"margin_type":"Percentage"}}` → `choices: []`, `note: "all links and choice values resolved"`. Consistent with the pre-existing Link behaviour, but it is a third path into a false all-clear (see findings 2, 4, 5) on a tool whose entire value is the trustworthiness of that note. | Consider a single "N supplied value(s) could not be interpreted" clause covering findings 2, 5 and 10 at once. |
| 11 | MINOR | `jarvis/tools/resolve_links.py:343` | `c["value"].casefold()` and `c["label"].casefold()` are recomputed for every supplied value against every option. 200 values × 1005 options = ~400k casefolds per request (measured acceptable in flow B21, so this is efficiency, not a break). | Fold once in `_parse_options` and carry the folded forms. |
