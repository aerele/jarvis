### Owner's four questions — direct answers

1. **Do the terminal paths still revoke?** Yes. No path found where a customer who should be suspended now is not, and none where money is gone and entitlement survives. Operator console cancel writes `status="Cancelled"` at `api/console.py:708` *before* `release_mandate` at `:714`, so its echo hits the `sub.status == "Cancelled"` guard at `webhook.py:535`. Full refund and lost dispute both arrive on their own webhooks and revoke through the shared `incidents.revoke_entitlement_for_money_loss` — proven live (sub `Cancelled`, customer `Suspended`, `User.enabled=0`). One pre-existing gap I note but do not raise against this diff: `_handle_refund` resolves only by `razorpay_order_id`/`razorpay_payment_id`, so a full refund of a *non-latest* autopay cycle matches nothing and never revokes. Unchanged by this change and already documented in the handler.
2. **The superseded-mandate echo.** See finding 3. Your guard cannot execute; your ordering is what protects you, and it holds at all five swap/clear sites. No window found where a live paying mandate is disarmed.
3. **The `cancel_plan_at_period_end` branch.** Idempotency holds (two parallel HTTP cancels → both OK, one release, no `cancelled_at`); an Expired sub carrying a dead mandate id gets `NotCancellable`, not a silent OK (confirmed live); a concurrently-arriving gateway echo is a no-op from either direction. The one-shot branch is behaviourally unchanged, not byte-for-byte (detail in edge 18 above). The guard reordering — refusals now before the idempotent return — is an improvement and is covered.
4. **(a)** Not acceptable as silence → finding 2 (MAJOR). **(b)** The entitlement worry is **unfounded**: `Pending Payment` is already in `ENTITLED_STATUSES` (`billing/entitlement.py:10`), so Past Due grants nothing it did not already have, and the row has no container. The flip is harmful for an entirely different reason — finding 1.
