## Attack pass (beyond the plan's list)

- **Type confusion on the new parameter** — `dict` / `list` / `int` `target_plan` refused at the tenant's
  own signature boundary (FrappeTypeError) before any admin round trip. Verified live. Defended.
- **Injection / traversal / oversize in `target_plan`** — reaches `frappe.db.get_value` as a
  parameterised docname; no SQL surface. Oversize is reflected in the refusal message (finding 12).
- **IDOR** — both new endpoints take no arguments; the subscription is resolved from the admin-side
  session (`current_customer()`). No handle a caller can aim. Defended.
- **Mandate release on supersede** — the new `_blocks_supersede` lets an APPLIED intent be superseded,
  and the retry branch calls `_enqueue_release`; `_enqueue_release` returns early on committed money
  and `release_superseded_object` re-checks under lock (`intent_ledger.py:791-830`), so a live mandate
  is never released by the new path. Defended — this was my first hypothesis and it is closed.
- **Check-then-act on money** — `scheduled_plan` staged outside the lock the claim takes: findings 3 and 4.
- **Unbounded work** — `_reactivation_plans` uncapped (finding 11); the healer is now IP-rate-limited
  (round-1 finding 7 closed), though `_bust_chat_gate`'s Redis KEYS scan still fires per successful
  check (it is wrapped in try/except, so it cannot lose the answer).
- **Offer/accept resolution divergence** (plan open question 4) — `get_account_summary` resolves via
  `_current_subscription` (prefers a serviceable row), `renew()` takes most-recent-overall. Real, but
  it needs a multi-subscription customer AND a direct API call: the pane renders no CTA in the
  divergent case, and renew re-checks `can_reactivate` on the row it resolved, so nothing mis-charges.
  **Decision: it does not block this plan; it needs its own plan** — the new `scheduled_plan` write
  makes it mutate a row the offer never described, which raises the cost of leaving it alone.
