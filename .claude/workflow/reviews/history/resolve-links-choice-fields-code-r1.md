**Verified, not findings** (checked and clean):
- Back-compat of `links[]`: every record still carries `target_doctype`; no consumer anywhere in the bench, plugin, or frontend reads the `resolve_links` response shape (only `registry.py` names it), so `choices` is purely additive.
- Case-sensitive exact match: matches `_validate_selects`, which compares the *stripped value* against the raw option list — `_resolve_choice` also strips the needle. `"open"` correctly surfaces as a candidate for `"Open"`.
- Options parsed once per field, not per child row: `_choice_fields(child_meta)` is hoisted above the row loop (`resolve_links.py:69`). Measured: 500 child rows → 500 records in 0.00s; 200 values × 1005 options → 0.04s.
- No SQL reaches the choice path — pure Python string matching, so hostile input (`' OR 1=1 --`, `%`, `_`, emoji, 20 000 chars) is inert. Confirmed by probe.
- No new information disclosure: `get_schema` already returns Select option values for the same doctype, so `choices` exposes nothing new.
- `limit` boundary guard (0, −1, 21, 20) behaves correctly and is enforced before any option scanning.
- Plugin descriptor is text-only; `jarvis__resolve_links` is already in `openclaw.plugin.json`, so no manifest touchpoint is missing. `npm test` → 250/250, including `tool-contract.test.ts`.
- `ruff check`, `ruff check --select=I`, `ruff format --check` at the pinned v0.14.10: all clean.
